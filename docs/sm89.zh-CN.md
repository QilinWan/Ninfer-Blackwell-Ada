# NInfer Ada（sm_89）移植说明（中文）

> 本页是英文权威文档 [docs/sm89.md](sm89.md) 的中文镜像；两者以英文版为准，
> 中文版同步到同一提交。产品行为（CLI、HTTP 服务、权重转换、模型语义）仍属上游，见
> [文档地图](README.md)。

本仓库在上游 [Neroued/ninfer](https://github.com/Neroued/ninfer)（只编译 `sm_120a`，即 RTX 5090）
之上，新增一套 **Ada（`sm_89`）** 构建：RTX 4090 / 4090D / 4080（SUPER）/ 4070（Ti）/ 4060。
**同一份代码、同一套 v3 `.ninfer` 权重、同一种对话质量**，也能跑在保有量最大的这代消费卡上。

## 一句话结论

上游把权重容器从 v2 换成 v3 时，**只改了容器与清单，量化后的权重字节没变**
（上游自带的 `tools/upgrade_ninfer_v2_to_v3.py` 就是"重新打包、不重量化"的活证据）。
因此我们**以 `master` 为基座**，而不是以某个 v2 时代的老分叉为基座：这样吃 v3 是白送的，
上游继续演进时用 `git merge` 跟进即可，而不是每次重写一遍移植。

## 支持矩阵

| | Ada（`-DCMAKE_CUDA_ARCHITECTURES=89`） | Blackwell（`120a`，上游默认） |
|---|---|---|
| 权重容器 | **仅 v3** | 仅 v3 |
| 权重档 | `groupwise-int`（Q4/Q5/Q6/Q8 + Q8 词表） | groupwise-int、`nvfp4` |
| 投机解码 | MTP、DFlash、DFlash2 | 同左 |
| KV 缓存 | INT8、FP8、BF16 | 外加 NVFP4、K8V4 |
| 多模态（图/视频） | 支持，需 FFmpeg ≥ 6（见下） | 同左 |
| CLI / HTTP 服务 | 支持 | 支持 |

一份 cubin 覆盖整个 Ada 家族：SM 数、L2 大小、常驻度全部**运行期从设备读取**，
所以 4090（128 SM）、4090D（114 SM）、4080 SUPER（80 SM）共用同一二进制。

## 快速构建

> 不想自己编？直接用预编译包
> **[engine-sm89-cu128-r2](https://github.com/QilinWan/Ninfer-Blackwell-Ada/releases/tag/engine-sm89-cu128-r2)**
> —— Ada `sm_89` / CUDA 12.8 / 带多模态，自带依赖（宿主无需 CUDA 工具链与编译器），
> 含 `rk4v4-e8` 与静态 YaRN 全部修复。

```bash
git clone https://github.com/QilinWan/Ninfer-Blackwell-Ada.git && cd Ninfer-Blackwell-Ada

# Ada（RTX 40 系）
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=89
cmake --build build -j

# Blackwell（RTX 5090）：与上游完全一致
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_CUDA_ARCHITECTURES=120a
cmake --build build -j
```

依赖：64 位 Linux、CMake ≥ 3.28、C++20、Ninja/Make、**CUDA ≥ 12.8**（Ada 侧保留的 FP4 解码路径要 `<cuda_fp4.h>`，12.8 起才有；12.6 会在配置期直接告诉你）、`pkg-config`；
开 `NINFER_BUILD_APPS=ON`（CLI/服务）还需 `libcurl ≥ 7.85`；开视觉需 FFmpeg ≥ 6 开发库。
纯文本构建可用 `-DNINFER_ENABLE_VISION=OFF` 免掉 FFmpeg 依赖。

⚠️ **Blackwell（`120a`）侧的 CUDA 地板是 13.0，不是 12.8**：Q8 k-split / NVFP4 路线在非 wide-column
调度下把 >48 KB 的 staging union 放在静态 `__shared__` 里（上游同款写法），而 CUDA 12.x 的
ptxas/nvlink 仍按 48 KB 静态共享内存上限校验 `sm_120a`——**12.8/12.9 会把 419 个 TU 全部编过，然后
倒在 `ninfer_ops` 的 device link 上**，报 `uses too much shared data (… 0xc000 max)`（59 个 kernel）。
13.0 起该上限放开，13.1/13.2 实测可编。Ada 侧不受影响：`NINFER_SM89` 分支会把超 48 KB 的 union 改走
dynamic window。配置期已加硬校验，12.x + `120a` 会直接报错而不是编 30 分钟后才失败。

## 踩过的坑（每个都会咬一台新 Ada 机器）

1. **FFmpeg 版本地板**：视觉解码用的是 FFmpeg 6 的 `av_packet_side_data_get`；
   Ubuntu 22.04 只有 `libavcodec 58`，会在 `decode.cpp` 深处编译失败。我们把检查提前到配置期，
   报错会直接告诉你装到的版本，并指向 `-DNINFER_ENABLE_VISION=OFF`。
2. **自编译 FFmpeg 别丢 zlib**：`--disable-autodetect` 会顺手关掉 zlib，PNG 解码器随之失效，
   即使全部编译通过，图像输入仍会报 *"media codec is not supported"*。保持 autodetect 开启，
   或显式 `--enable-zlib`。
3. **`libstdc++` 抢库**：当 `/root/miniconda3/lib` 之类目录在库搜索路径里时，链接器塞进来的 conda
   `libstdc++` 版本偏旧、缺 `GLIBCXX_3.4.30`，二进制能编出来但一启动就死。用系统的
   `LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libstdc++.so.6`，或换一个不牵连 conda 运行时的 `libcurl`。
4. **私有 FFmpeg 前缀不在加载路径**：自装的 `libswresample/libswscale` 需要
   `LD_LIBRARY_PATH=<prefix>/lib`，否则 `error while loading shared libraries`。
5. **`libcurl ≥ 7.85`**：Ubuntu 22.04 自带 7.81，开 apps 会卡在配置期；用 24.04+ 或自带一份 curl。
6. **Ada 协同启动常驻度是"每架构寄存器事实"**：GDN 门控投影的 cooperative 网格预算在 Ada 上更小
   （见 `cooperative_resident_ctas_per_sm`），沿用 sm_120a 常数会 `cudaErrorCooperativeLaunchTooLarge`。
7. **`--thinking-budget` 与 `--max-new`**：思考预算太接近输出上限会报"闭合控制后缀放不下"，
   给 post-close 至少留一个 token。

## 权重从哪来

不需要为 Ada 单独准备权重。两种途径：

* 直接下载官方/社区 **v3 `groupwise-int`** 产物（`model-cards/` 与各模型卡有链接）；
* 用上游 `tools/convert`（离线转换）或 `tools/upgrade_ninfer_v2_to_v3.py`（把已有 v2 重新打包成 v3，
  不重量化、不重新下载）。

## 启动与多模态

视觉投影器**打包在 `.ninfer` 容器内**，没有独立 mmproj 文件；未选中的组件不占显存。
读一下自己产物的 v3 清单即可确认它含哪些组件（`components`：`text` / `vision` / `mtp`|`dflash2`）：

```bash
# 文本 + MTP
./build/apps/ninfer model.ninfer --prompt "……" \
  --max-context 262144 --kv-dtype int8 --spec mtp --draft-tokens 3 --lm-head-draft --vision

# 文本 + DFlash2（--lm-head-draft 在 Ada 上两个头都是正收益，见下方实测）
./build/apps/ninfer model.ninfer --messages messages.json \
  --max-context 262144 --kv-dtype int8 --spec dflash2 --draft-tokens 7 --lm-head-draft --vision
```

## 实测吞吐（调优后，2026-09-24）

同卡（RTX 4080 SUPER 32 GB）、两个 Qwen3.8-27B `groupwise-int` 产物，贪心、INT8 group-64 KV、
`--prefill-chunk 2048`、单并发、512 新 token；解码为不含 prefill 的相速率。原始日志与一键脚本
（`mtp-best.sh` / `df2-best.sh`）见报告仓库。

| 产物 | 最佳投机配置 | 代码 | 结构化 | 数学 | 叙事 | 无投机 |
|---|---|---:|---:|---:|---:|---:|
| `…-mtp` | `--spec mtp --draft-tokens 3 --lm-head-draft` | 88.1 | 111.2 | 101.3 | **75.2** | 40.1 |
| `…-df2` | `--spec dflash2 --draft-tokens 7 --lm-head-draft` | **100.9** | **149.6** | **116.8** | 64.5 | 40.1 |

单位为 tok/s。K 扫描（四场景均值）：MTP K=2/3/4/5 = 80.5 / **91.4** / 84.4 / 84.0（草稿头训练窗即
3，K=6 被拒）；DFlash2 K=3/5/7/9 = 93.4 / 98.5 / **101.0** / 81.6，K>9 断崖。生成长度到 1024 token
时 K=5（97.7）反超 K=7（90.3），长输出求稳用 K=5。`--lm-head-draft` 两档必开（MTP +9%，
DFlash2 +5~11%；早前"Ada 上 DFlash2 加 lmd 更慢"的一次采样未复现）。KV 档位：INT8 最优
（fp8 -2~-10%，NVFP4/K8V4 在 Ada 构建期即拒绝，见上文路由报错）。`--no-thinking` 两档均 +16%。
prefill 6.8K prompt 为 1.45-1.52k tok/s（chunk 512-4096 无差）。

服务端：`--max-context 262144 --kv-capacity 262144` 共享 INT8 池，KV payload 8.77（MTP）/
8.25 GiB（DFlash2）；C=1/2/4 聚合 = 80.2/121.8/142.8（MTP）、85.3/109.2/159.1（DFlash2）tok/s，
C=4 时显存余量仅 1.76 GiB；C=8 + 满上下文启动被 reservation 拒绝（权重后需 ~17.1 GiB，仅 ~13.6
可用）。质量抽查：INT8 对 BF16 的 PPL 差 +0.025%（15.8K token 英文样本）；投机输出与无投机
5 次运行逐字节一致。

多模态：`--vision` + 图像 message 成功解码一张 PNG 图表、读出标题与计数、正常 `stop-token` 结束；
视频展开 ~1.2K prompt token，vision encode 67 ms，不拖解码速度。

## 实测数据：4-bit KV、上下文外推与全功能共存（sm_89）

以下数字全部来自单张 32 GB Ada 显卡（RTX 4090 级别）于 2026-09-25 运行 27B
`qwen3.8-27b-lynn-*` 产物、以本仓库源码构建（`NINFER_ENABLE_VISION=ON`）的实测结果，
非推算值。

### 4-bit KV（`--kv-dtype rk4v4-e8`）

| 检查项 | 实测结果 |
| --- | --- |
| 文本生成 | 答案正确、行文连贯 |
| DFlash2 接受率 | 36.1% / 41.8%（两次请求）|
| 解码吞吐 | 83.4 / 91.5 tok/s |
| KV 占用 | 每 token 18.28 KiB（16 个全注意力层 × 4 个 kv head × 260 B）|

`k8v4` 在此平台上**刻意不可用**：其路由需要 Blackwell 的 FP4 转换、块缩放 MMA 与 TMA，
`src/ops/sm89/nvfp4_sm89_stubs.cpp` 会直接报错而不是算出错误结果。Ada 上的 4-bit KV
路由是 `rk4v4-e8`（K 与 V 均为 4-bit）。

### 上下文上限（实测，非外推）

| 配置 | 最大上下文 | 显存 |
| --- | --- | --- |
| 裸跑（`--kv-dtype rk4v4-e8`，无多模态、无投机）| **约 820,000 token** | 31.2 GiB |
| `--vision --spec dflash2` + `--max-concurrency 2` | **约 544,000 token** | 30.3 GiB |
| 1,048,576 token（1M）| **装不下** | 约需 34.7 GiB → 需 48 GB 级显卡 |

1M 被拒是**显存预算判定**，不是软件限制：引擎报
`minimum Engine runtime reservation requires 19,134,598,912 bytes ... but only
16,432,955,392 bytes are available after weights`。

### YaRN 外推

`--rope-yarn-factor 4 --rope-original-max-position 262144` 达到产物原生窗口的 **3.13 倍**。
`validate_target_options` 中的位置上限对目标模型、草稿模型与因果注意力包络**都跟随因子**；
切分几何本身已随 `max_visible_keys` 缩放，因此无需改动内核侧限制。

### 投机解码路线选择

同产物同参数下 **MTP 优于 DFlash2**：接受率 63.2% / 66.7%（DF2 为 36.1% / 41.8%），
解码 81.8 / 83.0 tok/s（DF2 为 83.4 / 91.5 tok/s）；且其草稿模型更小，省下的显存被
自动分配为更大的 KV 池（693,888 vs 544,128 token），故总显存反而略高。

**MTP 产物请放在本地盘**：从 `/autodl-fs` 读取加载仅 60 MiB/s（耗时 4m40s），
而从 `/root/autodl-tmp` 为 6.65 GiB/s（耗时 2.7s）。

## 实测：sm_120a（RTX 5090）上的 NVFP4 KV，以及 DFlash2 为何不可用

测量时间 2026-09-25/26，单张 32 GB RTX 5090（sm_120a，驱动 595.71.05），目标产物
`qwen3.8-27b-lynn-nf4.ninfer`、草稿产物 `qwen3.8-27b-lynn-mtp.ninfer`，引擎以本仓库源码
按 `CMAKE_CUDA_ARCHITECTURES=120a` 与 `NINFER_ENABLE_VISION=ON` 构建。

### 上下文上限（实测，`--kv-capacity auto`，YaRN 因子 4）

| 配置 | 最大上下文 | 显存 |
| --- | --- | --- |
| 裸跑（`--kv-dtype nvfp4`，无多模态、无投机）| **约 790,000 token** | 768,000 通过（30.9 GiB），820,000 被拒 |
| `--vision` | **约 730,000 token** | 720,000 通过（30.5 GiB），760,000 被拒 |
| `--vision --spec mtp --draft-tokens 3 --max-concurrency 2` 加下列调优项 | **580,000 token** | 30,948 MiB，KV 池 588,288 token |

每一次被拒都是**显存预算判定**（`minimum Engine runtime reservation requires ...`），
不是软件限制；`--kv-capacity auto` 独立于 `--max-context` 决定 KV 池大小，所以在不释放
其它内存的前提下把 `--max-context` 提到上限之上并无收益。调优项（`--lm-head-draft`、
更深的请求队列、视觉预处理线程）各自占显存，因此**全调优配置的上限低于裸跑配置**。

### DFlash2 在此产物上不可用，原因如下

```
FATAL server failed during startup | linear_topk: unsupported head profile
```

`linear_topk` 是 DFlash2 草稿的候选选择器（对应产物元数据里的 `dflash_config.selector_rank`
与 `selector_top_k`）。`src/ops/linear_topk/linear_topk.cpp` 只接受三种头权重格式：

| 接受的 `qtype` | |
| --- | --- |
| `QType::Q8_G32_FP16` | full-head 形态 |
| `QType::FP8_E4M3FN_ROW_BF16` | full-head 形态 |
| `QType::Q4_G64_FP16` | optimized-head 形态 |

而 `nf4` 产物把这个选择器头也量化成了 NVFP4 —— 不在列表内，因此服务**直接拒绝启动**，
而不是算出一个错误的选择器。

这是**权重转换的疏漏，不是引擎缺陷**：目标权重以 NVFP4 正常加载
（`weights ready | 17.3 GiB | 12.9 GiB/s`），只有该选择器头受影响。修法二选一：把这一个
张量重新转换成受支持的格式，或给 `linear_topk` 增加 NVFP4 通路。

**MTP 不受影响**，是本机上可用的投机解码路线。

### Ada（sm_89，`rk4v4-e8`）与 Blackwell（sm_120a，`nvfp4`）对照

| | Ada 32 GB，`rk4v4-e8` | 5090 32 GB，`nvfp4` |
| --- | --- | --- |
| 裸跑上限 | 约 820,000 token | 约 790,000 token |
| 带多模态 | 约 720,000 token | 约 730,000 token |
| 4-bit KV 成本 | 每 token 每 kv head 130 B | 每 token 每 kv head 144 B |
| DFlash2 | 可用 | 受上述选择器格式阻塞 |
| MTP | 可用（接受率 63~67%）| 可用 |

两条路线的结果相差几个百分点，与每 key 体积约 10% 的差异相符。`rk4v4-e8` 按设计是
**Ada 专属**；sm_120a 构建会剔除它并链接 NVFP4/K8V4 路由，因此 `--kv-dtype` 的可用取值
**按显卡不同是正常的**。
